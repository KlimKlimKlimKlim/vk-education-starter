# Практическое задание 9: корутины

## Отмена установки

`AppDetailsState.Content.installState` имеет состояния `NotInstalled`, `Installing(progress)` и `Installed`.
`AppDetailsViewModel` хранит `private var installJob: Job?` и запускает установку через `installJob = viewModelScope.launch { ... }`.
Сразу выставляется `Installing(0)`, затем `emulateInstall()` каждые 150 мс после `delay(150)` добавляет 5% вплоть до 100%; по завершении выставляется `Installed`.

Кнопка показывает «Установить» → «Отменить» → «Установлено» (последнее состояние недоступно для нажатия).
Повторный клик во время установки вызывает `installJob?.cancel()`, сбрасывает ссылку на Job и возвращает `NotInstalled`.
`delay` — точка отмены: отменённая корутина не продолжает обновлять прогресс. Состояние обновляется через `MutableStateFlow.update`, не затирая остальные поля карточки.
При быстром двойном клике отменяется даже ещё не начавшая выполняться Job; новая установка начинается с 0%.
При повороте та же ViewModel продолжает установку; при удалении карточки из back stack ViewModel очищается и её дочерняя работа отменяется.
Это эмуляция: APK не скачивается и системный установщик не вызывается. Постоянное хранение состояния установки заданием не предусмотрено.

## Загрузка рейтингов

`AppsApi.getRating(id)` использует `delay(1500)` и `(30..50).random() / 10f`: симулируется запрос с рейтингом от 3.0 до 5.0.
Для реальных HTTP-методов выделен `RetrofitAppsService`; обычный `RetrofitAppsApi` оборачивает его и наследует локальную suspend-реализацию рейтинга. Retrofit не пытается интерпретировать неаннотированный `getRating` как HTTP-эндпоинт.
Репозиторий делегирует получение рейтинга в API, а `LoadRatingsUseCase` реализует оба способа:

- Последовательно: `ids.associateWith { repository.getRating(it) }`, следующий suspend-вызов начинается после предыдущего.
- Параллельно без ограничений: `coroutineScope { ids.map { async { ... } }.awaitAll().toMap() }`, все запросы — дочерние корутины одного scope; semaphore/лимита нет.

В каталоге есть две кнопки. Сначала нажмите «Рейтинги: последовательно», дождитесь окончания, затем «Рейтинги: параллельно».
`AppListViewModel` измеряет каждый способ через `measureTimeMillis`, хранит обе длительности и последний набор рейтингов; время и количество приложений выводятся рядом с кнопками, рейтинг — в каждом элементе списка.
Во время выполнения обе кнопки недоступны. Ошибка рейтингов не убирает каталог и допускает повтор; `CancellationException` не проглатывается.
При повороте рейтинги не перезапускаются: загрузка и результат находятся в ViewModel.

## Реальный замер на 12 приложениях

Замер выполнен 15 ноября 2026 года на Linux x86_64, OpenJDK 17.0.21, Kotlin JVM 2.0.21, kotlinx-coroutines 1.9.0.
Запущен `RatingsBenchmarkTest.compareTwelveAppsWithRealDelay` через Kotlin JVM compiler + JUnitCore.
Использованы реальные задержки, `runBlocking` и `measureTimeMillis`, не виртуальное время `runTest`.
Это автономный benchmark 12 различных id из серверного каталога, а не запрос реальных рейтингов: сервера рейтинга по условию нет. Используются настоящие `AppsApi.getRating` и `LoadRatingsUseCase` приложения; получение HTTP-каталога не входит в измерение.

| Способ | Количество приложений | Фактически измерено |
| --- | --- | --- |
| Последовательный | 12 | 18 007 мс |
| Параллельный без ограничений | 12 | 1 501 мс |

Фрагмент фактического вывода автономного запуска:

```text
JUnit version 4.13.2
..............RATINGS_BENCHMARK count=12 sequentialMs=18007 parallelMs=1501
.
Time: 19.929

OK (15 tests)
```

Вывод: последовательная длительность близка к сумме 12 задержек по 1500 мс, параллельная — к одной задержке плюс накладные расходы. В этом запуске ускорение примерно 12 раз.
`async` даёт конкурентное ожидание, а не обязательное выполнение на 12 потоках: `delay` не блокирует поток.
`coroutineScope` ждёт дочерние работы; отмена родителя отменяет все запросы, ошибка одного дочернего запроса отменяет соседние. Это проверяется unit-тестами.
Рейтинги при двух запусках могут различаться из-за `random()`, как и предусмотрено условием.
UI загружает рейтинги для всех полученных приложений, не обрезая список до benchmark-выборки. Поэтому его длительность зависит от размера текущего каталога.

## Воспроизведение

Обычные unit-тесты используют виртуальное время. Долгий benchmark по умолчанию пропускается через JUnit assumption.
PowerShell, из корня проекта с установленными JDK и Android SDK:

```powershell
.\gradlew.bat :app:testDebugUnitTest
$env:RUN_RATINGS_BENCHMARK = "1"
.\gradlew.bat :app:testDebugUnitTest --tests "*RatingsBenchmarkTest" --rerun-tasks
Remove-Item Env:RUN_RATINGS_BENCHMARK
```

Вывод benchmark доступен в test report / XML из `app/build/test-results/testDebugUnitTest/`. Миллисекунды на другой машине могут отличаться.

## Самопроверка на телефоне

1. Открыть карточку → «Установить»: появляется «Отменить» и растущий процент.
2. До окончания нажать «Отменить»: снова «Установить», прогресс исчезает и не продолжает расти.
3. Нажать «Установить» повторно: прогресс начинается с нуля, примерно через 3 секунды — «Установлено», кнопка недоступна.
4. Дважды быстро нажать кнопку в начальном состоянии: установка отменяется; затем её можно начать ещё раз.
5. Повернуть телефон во время установки: прогресс сохраняется, новая установка не запускается.
6. Начать установку, выйти назад, снова открыть карточку: старой установки нет.
7. В каталоге выполнить последовательную загрузку рейтингов, затем параллельную: возле приложений появляются звёздочка и число, над списком — обе длительности и размер каталога.
8. Повернуть телефон во время загрузки рейтингов: запросы не стартуют заново.
